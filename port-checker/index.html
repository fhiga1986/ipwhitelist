What is a port checker?

A port checker tests whether a specific TCP port on a remote host is accepting connections. When a port is "open", it means there is a service listening on that port and it is reachable from your current network. When a port is "closed" or "filtered", either no service is running on that port or a firewall is blocking the connection.

Developers reach for a port checker in three situations: after deploying something new ("is my API actually reachable on 8080?"), while debugging a connection error ("is it the database or the security group?"), and when auditing exposure ("is my Redis instance visible from the internet?").

Common ports and their services

Ports 0–1023 are the "well-known" ports reserved by IANA for standard services; 1024–49151 are registered ports used by common software; the rest are ephemeral ports that clients pick at random. These are the ones developers test most often:

Why would a port appear closed or unreachable?

  1. Nothing is listening. The service crashed, never started, or runs on a different port than you think. Check with ss -tlnp (Linux) or netstat -ano (Windows) on the server itself.
  2. The service only listens on localhost. MySQL, PostgreSQL and Redis bind to 127.0.0.1 out of the box. They answer on the server but refuse everyone else until you change the bind address.
  3. A host firewall drops the packets. UFW, iptables, firewalld or Windows Defender Firewall. Allow the port, or better, allow it only from your IP.
  4. A cloud firewall drops them first. AWS security groups and network ACLs, GCP VPC firewall rules and Azure NSGs sit in front of the instance. Security groups drop silently, which is why cloud hosts usually show No response instead of Answered.
  5. Your own network blocks the way out. Corporate proxies often allow only 80 and 443; many ISPs block 25, 135–139 and 445. The same port can look closed from the office and open from your phone.
  6. NAT without port forwarding. A home server behind a router needs a forwarding rule on the router — the public IP belongs to the router, not to the server.

If the port should be open for you specifically, add your current public IP to the firewall rule — the IP whitelist config generator produces the exact AWS, GCP, UFW and iptables commands with your address already filled in.

How this browser-based port check works

Browsers deliberately cannot open raw TCP sockets, so a web page cannot run a real port scan. Instead, this tool asks your browser to open an HTTPS connection to host:port and interprets what happens:

ResultWhat happenedWhat it means
OpenThe TLS handshake completedAn HTTPS/TLS service is listening. Definitive.
Open — service answeredThe host replied but TLS failed, and the same host silently drops unused portsA non-HTTPS service (database, SSH, plain HTTP) is almost certainly listening.
Answered — closed or non-HTTPSThe host replied but TLS failed, and the host actively refuses unused portsEither a closed port (connection refused) or a non-HTTPS service. A browser cannot tell these apart.
No responseNothing came back within 6 secondsA firewall is dropping packets, the host is offline, or the service waits for the client to speak first (plain HTTP on port 80 often behaves this way).
Not testable in a browserThe browser refused to connectThe port is on the browser's restricted list: 21, 22, 23, 25, 110, 143, 465, 587, 993, 995 and about sixty others.

To separate "closed" from "non-HTTPS service", the tool first probes a random high port on the same host. If that baseline port gets no response, the host drops unused ports — so any port that does answer must have a service behind it. If the baseline is actively refused, the host sends resets for closed ports, and an answer on your target port is ambiguous; the tool says so and prints the terminal command that settles it.

Because the probe runs from your browser, the result reflects your network path. A corporate proxy or VPN can make an open port look filtered, and a port that is open to the world can still be closed to you if the server's firewall only allows specific addresses.

How to check if a port is open from the command line

Command-line tools talk TCP directly and are not limited to HTTPS, so they give a definitive answer for any port — including SSH and mail ports that a browser cannot touch.

ToolCommandHow to read it
netcatnc -zv example.com 443"succeeded" = open · "refused" = closed · hangs/timeout = filtered
Bash built-intimeout 3 bash -c '</dev/tcp/example.com/443' && echo openWorks on servers where netcat is not installed
PowerShellTest-NetConnection example.com -Port 443TcpTestSucceeded : True means open
nmapnmap -Pn -p 22,80,443 example.comReports open / closed / filtered per port — the reference tool

Only scan hosts you own or have written permission to test. Unauthorised port scanning violates most providers' acceptable-use policies and may be illegal in your jurisdiction.

What is the difference between TCP and UDP ports?

TCP ports (Transmission Control Protocol) require a three-way handshake before data is exchanged, making them reliable and ordered. Web servers (port 80, 443), SSH (port 22), and databases (MySQL port 3306, PostgreSQL port 5432, MongoDB port 27017) all use TCP.

UDP ports (User Datagram Protocol) send data without establishing a connection first. This makes UDP faster but less reliable. DNS (port 53), NTP (port 123), WireGuard (51820) and most game and voice protocols use UDP. This port checker tests TCP only — a UDP port gives no reply when it is open, so it can only be tested by a tool that speaks the specific protocol (for example nmap -sU).

Port checker questions

Your browser opens an HTTPS connection to each host:port and the tool classifies the outcome: a completed TLS handshake means the port is open; a reply without TLS means the host answered (a closed port or a non-HTTPS service); no reply within 6 seconds means a firewall dropped the connection or the host is down. Results reflect what is reachable from your current network, so a corporate proxy or VPN can change them.
A closed port actively refuses the connection — the server answers with a TCP reset. A filtered port never answers because a firewall silently drops the packets. In this tool a closed port shows as "Answered" and a filtered one as "No response"; nmap labels them "closed" and "filtered" respectively.
Chrome, Firefox and Safari refuse to open connections to a fixed list of "unsafe" ports — among them 21, 22, 23, 25, 110, 143, 465, 587, 993 and 995 — to stop web pages from abusing other protocols. The refusal happens inside the browser before any packet is sent, so no web-based tool can test those ports. Use nc -zv host 22 or Test-NetConnection host -Port 22 from a terminal instead.
Open it at every layer between the internet and the process: the cloud firewall (an AWS Security Group inbound rule, a GCP firewall rule, an Azure NSG rule), the host firewall (sudo ufw allow from YOUR_IP to any port 5432 or the equivalent iptables rule) and the service itself (bind to 0.0.0.0 instead of 127.0.0.1). Always restrict the rule to your own IP in CIDR form rather than 0.0.0.0/0 — the whitelist generator writes those rules for you.
Testing your own servers, or systems you have explicit permission to test, is fine and is exactly what this tool is for. Scanning other people's infrastructure without permission breaches most providers' acceptable-use policies and can be a criminal offence under computer-misuse laws in many countries, even when nothing is broken into.
